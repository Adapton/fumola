fumola

An experimental programming language whose execution model is Adapton: a program's run leaves behind a graph of what it named, read and demanded, and that graph is what the next run reuses.

This host also serves the Fumola runtime compiled to WebAssembly — fumola_wasm.js and fumola_wasm_bg.wasm, in this directory. It is what the Hazel Fumola livelit loads, and what the box below is running.

The language

Fumola is two things joined. Its surface is conventional and borrowed: functions, records, variants, modules, pattern matching, arithmetic — taken from Motoko, whose Rust interpreter Fumola descends from. Those features are deliberately ordinary, so that they stay out of the way.

What is not ordinary is how a Fumola program runs. Its incremental primitives come from The Extended Adapton Recipe, including Demanded Computation Graphs extended with symbolic space and time. They are the subject of the rest of this page. 

public func gcd(a : Nat, b : Nat) : Nat {
  if (b == 0) { a } else {
    gcd(b, a % b)
  }
}

That is the whole of Gcd, one of the library modules compiled into the runtime. Nothing about it is incremental — it reads no cells, so there is nothing for Adapton to reuse. Most Fumola code looks like this. The primitives are what you reach for when you want a computation to survive being edited.

Adapton, briefly

Adapton is a way of running a program so that changing its input does not mean running it again. As the program executes it builds a demanded computation graph: a bipartite record of cells, which hold values, and thunks, which are suspended computations, with an edge for every action a thunk took — every cell it wrote, every cell it read, every thunk it forced — kept in the order it took them.

The graph exists so that a later run can be repaired rather than redone. When a cell changes, the thunks that read it are the ones whose results are in question; everything else in the graph is still good, and is reused as it stands. What makes this addressable at all is that every cell and thunk has a name: the run after the edit has to recognise the node it is about to recompute as the same node as last time, and a name is how it does.

Repair is where Fumola's own work is. The graph, its event history and its introspection are implemented; the realignment of a graph across an edit — signaling and repair, in the Recipe's terms — is the language's ongoing work rather than a finished feature. What the runtime does today is reuse a thunk's cached result on a cache hit, and record what it did either way.

The primitives

There are not many. Two ways to make a node, two ways to depend on one, one way to look without depending, and a way to say where the nodes you make should live.

thunk { e } Suspend a computation. A thunk is an ordinary Fumola value: it can be bound, passed and stored.
`n := e put. Write the value of e into the cell named `n, and evaluate to a pointer to that cell. Putting a thunk is how a named thunk comes to exist.
pointer(`n) The pointer that the symbol `n names, whether or not anything has been written there.
@p    get(`n) get. Read a cell, recording a dependency: an edge from the thunk doing the reading to the cell read. get(`n) is just @pointer(`n).
force(p) force. Demand the thunk at p, recording a dependency on it. A cache hit answers with what that thunk already computed; a cache miss runs its body.
peek(`n) Read a cell without recording anything. Answers an option, since the cell may never have been written.
do within space `s { e } Navigate. Names the region that the cells and thunks allocated inside e belong to, so that a subcomputation can allocate freely without colliding with its callers.
force(`n := thunk { e }) Not a primitive but the idiom the others are usually reached through: name a thunk, put a computation in it, demand it. Running it again with the same name is what an edit is.

The Fumola VS Code theme paints := and @ in their own color, distinct from every other operator. That is not decoration: put and get are the two effects the graph is a record of, and it is useful to see them from across the room.

Names are values

A name in Fumola is a symbol, and symbols are first-order data. An identifier is a symbol, written with a leading backtick; a number is a symbol; and symbols compose by application, as deeply as you like. So a name can be computed — which is what lets a recursive algorithm give each of its nodes a name derived from its position rather than from a counter. 

`hello                 // an identifier
7                      // a number is a symbol too
`adapton(`settings)    // application, and it nests

Space and time

The Recipe's extension is that a name has two dimensions, not one. Space is where a cell lives: put `x inside the region `region and the cell allocated is `region(`x), so a subcomputation can name things freely without colliding with its caller. Time is when it holds what it holds, which is what lets one name carry a history rather than a single value. Each is mostly just a symbol, and each has a relative form for the place evaluation happens to be: 

Adapton.here()         // the space we are in now
Adapton.now()          // the time we are at now
Adapton.space(`region) // a space named outright

Two modes, and why the distinction is load-bearing

A Fumola program runs in one of two modes, and which one it is in is decided by a single fact: whether a force is underway.

The archivist runs inside a force. Its operations are the tracked ones — put, get, and force itself — because there is a computation in progress for a dependency to be recorded against. Every edge in the graph is drawn by an archivist.

The editor is the more general mode, and always runs on a force-free stack. It is where changes come from. Resetting the store and reading the graph belong to it alone: asking for a reset from inside a force is not a meaningful request — it would pull the store out from under the computation making it — and Adapton refuses it.

peek is the interesting case. It belongs to the editor, but it stays available inside a force on purpose, because reading a cell without recording a dependency is exactly how you look at a computation while it runs. A peek in a thunk is meaningful; it is merely untracked.

Two semantics: graphical and simple

The primitives above have two implementations in the runtime, and an instance runs one or the other. Graphical is the default — it is what the VM constructs, what the REPL starts in, and what the examples throughout the repo run.

Graphical keeps the DCG proper: nodes, edges, each thunk's trace in the order it ran, and an event history stamped with a meta-time. It is the semantics the pictures on this page are drawn from, the one the introspection below reports on, and the one repair will need.

Simple keeps a store and no more: cells indexed by space and time, thunks with their cached results. Forcing a thunk that has already run answers with what it computed. It is predictable and cheap, and it keeps no graph, so there is nothing to introspect and nothing to repair. It has to be asked for by name — which the Hazel integration currently does, for a reason given below.

The graphical store reports on itself in Fumola's own value language, so a program can read its own history as ordinary data: 

// the event log: addNode, addEdge, forceBegin, forceEnd, ...
Adapton.peekEvents()    // [{metaTime; event}]
Adapton.peekInfo(p)    // one node, and the edges either side of it
Adapton.peekHistory()   // events, nodes and edges together

That is the hinge the rest of the tooling hangs on. Because the graph is readable as data from inside the language, a Fumola library can process its own past behavior into something to look at — the outlines, scenes and JSON exports in fumola/system/adapton — without any of it being built into the runtime.

Fumola in Hazel

Hazel is a live functional programming environment: every edit state has a meaning, so a program has a result even while it is incomplete. It has livelits — user-defined graphical literals embedded in the program text, which expand to the expression they stand for.

The experimental integration puts Fumola behind three of them. It is not on Hazel's default branch; it lives on fumola-livelit-mvp, and that branch has a live build you can open. 

# declare a runtime, and the Adapton semantics it runs #
let rt : Int = ^fumola_new(7, Graphical) in

# run a program as a named thunk, and use its result as a Hazel value #
let answer : Int =
  ^fumola_put_force(7, "`gcd", "Gcd.gcd(12, 18)") in

# read the graph the run left behind, as a table of records #
let events : [EventRow] =
  ^fumola_eval(7, "Adapton.peekEvents()") in

^^probe_table(events);

The three do different jobs, and the split is the archivist/editor distinction wearing editor clothes. ^fumola_put_force wraps its program as force(`n := thunk { … }), so it runs on a forceful stack — archivist mode, where the tracked operations live. That wrapper is also what gives an edit its incremental meaning: editing the program re-assigns the same name and re-forces it, so the thunk's history is reused rather than discarded. ^fumola_eval runs its program at the top level with no thunk around it — editor mode, which is where peek, reset and the graph introspection belong. ^fumola_new declares which semantics a runtime runs.

A livelit expands to a Hazel value, so Fumola's values have to cross: numbers, floats, booleans, tuples, records as labeled tuples, variants, arrays as lists, options, symbols as their text. A pointer crosses as a reference that carries what it points at, so it can be used as the value while still showing which cell that value came from. Values whose meaning depends on the runtime — a thunk, a function — cross opaque, carrying the source Fumola prints for them, and force is what turns one into something Hazel does have a value for.

Two incremental systems meet here, and how they compose is the open question: Hazel re-evaluating a program as it is edited, Adapton repairing a graph underneath it. So the Hazel integration inverts Fumola's default and starts a runtime simple, with graphical asked for by name. That is a conservative choice for the design phase this work is in rather than a settled one — the intent is for Hazel to default to graphical too, once the composed semantics is understood.

The runtime this host serves

Alongside this page: fumola_wasm.js, the wasm-bindgen glue, and fumola_wasm_bg.wasm, the runtime. Both are built from the fumola_wasm crate by .github/workflows/wasm-pages.yml on every push to main, and neither is checked in.

Published as a Pages site rather than as a release asset, deliberately: release downloads carry no Access-Control-Allow-Origin header, so a browser can never fetch one cross-origin — which is the only thing this artifact exists to do. Pages serves it with CORS and the right content type. 

import init, { fumola_create, fumola_eval_top }
  from "https://adapton.github.io/fumola/fumola_wasm.js";

await init();
const id = fumola_create();
fumola_eval_top(id, "`x := 41; get(`x) + 1");
// -> {"ok":true,"tag":"Int","value":"42"}

The glue and the .wasm are generated together and will not load if their versions disagree, so take both from the same place. Hazel prefers a locally built pair when there is one and falls back to this published build otherwise.
